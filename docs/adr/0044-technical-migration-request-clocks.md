# ADR-0044: проверка request clock в технической миграции

Дата: 2026-11-01. Статус: принято для реализации; установка проверяется отдельно.

## Причина

На заполненной копии native Forge миграция нескольких Git-подключений выполняет
backfill, затем `ALTER TABLE` в одной транзакции. Отложенный constraint trigger
`forge_human_request_clock` оставляет события после `UPDATE`, поэтому PostgreSQL
отказывает в последующем DDL. Пустые таблицы не воспроизводят ошибку.

## Решение

Общий loader `backend/migration/catalog.rs` используется сервером,
`cicd-migrate` и изолированным PostgreSQL helper. Внутри каждой транзакционной
миграции техническая настройка переводит существующий
`public.forge_human_request_clock` в режим `IMMEDIATE`. Trigger продолжает
проверять исходный срок подтверждения; проверки не отключаются. Режимы остальных
отложенных ограничений не меняются. Настройка заканчивается вместе с транзакцией,
поэтому обычные запросы сохраняют отложенную проверку на commit.

SQL-файлы выпущенных миграций, номера и SHA-384 их исходных тел сохраняются.
Настройка транзакции принадлежит версионируемому executable, как `BEGIN`,
`COMMIT` и запись SQLx history. Loader сохраняет исходный checksum тела и
добавляет настройку только к исполняемому представлению. Проверка всех applied
versions/checksums и advisory locking SQLx остаются обязательными.
`-- no-transaction` сохраняет исходное выполнение без этой настройки.

Для обновления заполненной БД используется `cicd-migrate` из проверенного
образа. Прямой `sqlx-cli` читает те же тела и checksums, но не устанавливает
технический режим request clock, поэтому не заменяет этот upgrade entrypoint.

Сверено с закреплённым
[SQLx 0.8.6](https://github.com/launchbadge/sqlx/blob/v0.8.6/sqlx-core/src/migrate/migrator.rs)
и [PostgreSQL 17: SET CONSTRAINTS](https://www.postgresql.org/docs/17/sql-set-constraints.html).

## Проверки

Реальный PostgreSQL fixture сначала воспроизводит отказ исходного SQLx на
заполненной таблице. Общий loader должен выполнить тот же backfill и DDL,
сохранив данные, исходные SQL body checksums и повторный запуск. Отдельно
проверяются отклонение изменённого тела, конкурентные migrators, неизменность
`no-transaction`, другой отложенный FK и отказ commit обычного запроса
с истёкшим подтверждением. Обе выпущенные истории и фактическая заполненная
копия production проходят самостоятельные gates до установки.
