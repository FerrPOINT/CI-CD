# ADR-0031: синхронизация hosted Git с внешним репозиторием

Статус: принято, 2026-10-17.

Кардинальность и идентичность подключения уточнены в
[ADR-0040](0040-multiple-repository-sync-connections.md): один репозиторий
допускает несколько независимых подключений. Остальные правила Git сохраняются.

Forge исполняет Git HTTPS сам, без provider mirroring, OAuth и CI runner.
Поддерживаются GitHub.com и операторский allowlist HTTPS origins GitLab.
Подключение принадлежит UUID hosted-репозитория. Настройки по умолчанию:
направление disabled, запуск manual. Автоматический режим сверяется каждые
300 секунд и объединяет сигналы push/PR merge в одну последующую сверку.

Domain решает направление каждого ref и конфликты; application проверяет
команду и использует ports хранения/шифрования; infra содержит PostgreSQL,
AES-GCM и ограниченные Git-процессы; HTTP и worker связывают эти компоненты.
Provider URL проверяется и канонизируется до передачи Git: backslash,
управляющие символы и credentials в authority запрещены. Allowlist сравнивает
тот же canonical origin, который получает Git, включая повторную проверку
сохранённых настроек worker-ом.

Токен хранится отдельно от pipeline secrets и передаётся credential helper
через наследуемый FD только соответствующему процессу. URL, argv, Git config,
readback и диагностика не содержат токен. Проверка TLS обязательна, redirects
запрещены; частный CA устанавливается в системное хранилище доверия.

Синхронизируются только heads/tags, без удаления, изменения HEAD, merge/rebase
и перезаписи истории. Перед push проверяются ancestry и ожидаемый старый SHA;
lease ref используется как compare-and-swap. По умолчанию защищённые ветки Forge, включая создание, требуют обычного PR.
Default branch каждого связанного проекта входит в защиту независимо от
явного списка protected branches, как в обычном Git receive.

Администратор-человек может явно выбрать для pull-подключения политику
protected_branch_updates=source_fast_forward. Worker вправе обновлять
защищённые ветки только fast-forward с прежним CAS и проверкой актуальной
версии connection перед записью. Обратная отправка и Both с такой политикой
недопустимы. Обычные Git receive/PR проверки не изменяются.
При отсутствии поля действует blocked; значение blocked не добавляется
при сериализации прежних settings и не меняет их fingerprint.
Право настройки возвращается HTTP adapter в
can_manage_protected_branch_updates; UI не угадывает его по имени/репозиторию.

Это не разрешение первичного overwrite расходящейся истории. Однократное
согласование refs принадлежит отдельной операторской операции с сохранением
прежних объектов и проверкой источника. Ни automatic sync, ни новый policy
не выполняют force-push, удаления refs или очистку исторических секретов.


Namespace admission захватывается перед общей файловой flock-блокировкой
репозитория. Receive-pack, PR merge и sync используют тот же inode. Git child
наследует блокировку: окончание DB lease не разрешает конкурентную запись,
пока старый процесс жив. Guard не захватывается повторно из post-receive hook.

Sync worker дополнительно проверяет живость самой admission-транзакции во
время Git. Потеря этого соединения не эквивалентна успеху отдельного heartbeat:
Git отменяется с ожиданием остановки процесса, результат остаётся reconciling
до сверки refs новым исполнением. OS guard удерживается до журналирования.

Общий concurrency ограничен также файловыми слотами на том же Git root,
унаследованными дочерними Git-процессами. PostgreSQL advisory slots координируют
работу, но потеря их сессии не освобождает физическую ёмкость живого helper.
Все workers используют одинаковый лимит; его снижение требует дренирования.

Таблицы запусков и refs образуют durable-журнал: намерения фиксируются до
Git-эффектов. При восстановлении ожидаемый SHA подтверждает передачу, прежний
SHA разрешает безопасное продолжение, иной SHA означает конфликт. Недоступный
провайдер оставляет reconciling. Отключение отменяет queued и запрашивает
остановку running; принятый push не объявляется отменённым без наблюдения.

Входящие refs оставляют durable CI-событие с точным SHA и общим с обычным
push ключом идемпотентности. Существующая push-policy выбирает конфигурацию
либо отключает запуск. Повторное наблюдение равных SHA ничего не передаёт.

Миграция 0093 аддитивна. История и snapshots сохраняются при смене адреса,
credentials и отключении. Worker flag изначально false; существующие
репозитории автоматически не подключаются. Установка кандидата в runtime —
отдельный этап после проверки совместимости миграций и smoke. Обычная разработка
не требует backup/restore. Откат выключает worker,
сохраняет PostgreSQL/Git/history; down migration и удаление volumes запрещены.
