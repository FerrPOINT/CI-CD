# ADR-0016: Сериализуемая выдача runner work

**Статус:** Accepted (2026-09-21)

## Контекст

`work:poll` одним SQL statement проверял число активных lease проекта и создавал
новый lease. При `READ COMMITTED` два конкурентных poll могли прочитать снимок
до фиксации другого claim и оба выдать работу при `max_running_jobs=1`.
Блокировка строк очереди или проекта с `SKIP LOCKED` сама по себе не обновляет
снимок statement после ожидания.

## Решение

- Выполнять внешний claim в транзакции PostgreSQL `SERIALIZABLE`.
- Повторять только конфликт сериализации `40001`, каждый раз с новым lease ID и
  токеном. После восьми конфликтов возвращать `204` с warning: существующий
  runner продолжит polling, а работа не будет выдана сверх квоты.
- Не менять формат runner protocol, квоту и схему БД. Проверять конкурентные
  poll двух runner-ов реальным PostgreSQL-тестом и считать lease по проекту.

## Последствия

Возможны дополнительные короткие повторы при высокой конкуренции, зато
активных внешних lease не становится больше проектной квоты. Неуспешная
транзакция не публикует lease token и не оставляет частично выданной работы.
