# Релизы Forge CI/CD

## Версионирование

Проект использует Semantic Versioning: `MAJOR.MINOR.PATCH`.

- `MAJOR` — несовместимые изменения публичного REST API, CLI, конфигурации или схемы развёртывания.
- `MINOR` — обратно совместимый функционал, например новая возможность control plane.
- `PATCH` — обратно совместимые исправления, документация или обновления зависимостей без изменения контракта.
- До первой стабильной версии допустима серия `0.x.y`; несовместимость отражается повышением `MINOR`.

Тег релиза имеет вид `vMAJOR.MINOR.PATCH`, например `v0.2.0`. Релизный номер должен быть согласован с `backend/Cargo.toml`, если crate публикует или показывает собственную версию.

## Changelog

История изменений ведётся в `CHANGELOG.md` в корне репозитория в формате Keep a Changelog. Для каждого релиза указываются дата и ссылка на тег; записи группируются по разделам `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`.

```markdown
## [0.2.0] - YYYY-MM-DD

### Added
- Поддержка ...

### Fixed
- Исправлена ...
```

Перед выпуском изменения сначала находятся в секции `Unreleased`. В changelog описывается пользовательский эффект, а не внутренний список файлов или хешей коммитов. Breaking changes выделяются явно с инструкцией миграции.

## Подготовка

1. Убедиться, что рабочее дерево чистое и CI для целевой ветки успешно завершён.
2. Сверить функциональность, ограничения и известные проблемы с `README.md`, `docs/ROADMAP.md`, `docs/API.md` и ADR.
3. Обновить версию, `CHANGELOG.md` и при необходимости документацию миграции.
4. Проверить `.env.example`: он содержит все обязательные несекретные `CICD_` переменные, актуальные имена и безопасные примеры. Реальные пароли, токены и production URL в него не попадают.
5. Выполнить backend, frontend и контейнерные проверки из раздела ниже.

## Проверка кандидата

```bash
# Backend запускается в контейнере, чтобы не зависеть от Rust toolchain хоста.
docker run --rm --entrypoint /bin/bash -v "$PWD/backend:/workspace" \
  -w /workspace rust:1.86-bookworm \
  -lc '/usr/local/cargo/bin/cargo fmt --check && /usr/local/cargo/bin/cargo clippy --all-targets -- -D warnings && /usr/local/cargo/bin/cargo test && /usr/local/cargo/bin/cargo build --release'

cd frontend
pnpm install --frozen-lockfile
pnpm test
pnpm build
cd ..

docker compose config
docker compose build
```

Если окружение допускает запуск сервисов, добавить smoke-проверку:

```bash
docker compose up --build -d
curl -fsS http://127.0.0.1:22801/api/v1/health
docker compose down
```

## Процесс выпуска

1. Создать отдельный release commit с версией, changelog и обновлённым `.env.example`.
2. Отправить commit в `main` после прохождения review и GitHub Actions.
3. Создать аннотированный тег и отправить его:

```bash
git tag -a v0.2.0 -m "Release v0.2.0"
git push origin v0.2.0
```

4. Собрать Docker-образы backend и frontend из этого неизменяемого тега. Публиковать как минимум тег версии (`v0.2.0`), а `latest` обновлять только для согласованного стабильного релиза.
5. Проверить образы: запустить compose с опубликованными тегами и запросить `/api/v1/health` на API `22801`.
6. Создать GitHub Release на основе тега: краткое описание, ссылка на соответствующий раздел changelog, breaking changes, инструкции обновления и digest/теги образов.
7. После публикации зафиксировать результат в релизной задаче и наблюдать первые развёртывания.

## Откат

Тег релиза неизменяем. При регрессии не переписывать опубликованный тег и не заменять образ с версионным тегом. Выпустить новый patch-релиз или явно задокументировать возврат на предыдущий известный тег. Откат схемы PostgreSQL планируется только через заранее проверенные миграции; до их появления изменения схемы должны быть обратно совместимыми.
