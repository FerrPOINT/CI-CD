# Хранение данных Forge CI/CD

## Текущее состояние

В MVP единственное постоянное хранилище — PostgreSQL 17. В нём находятся проекты, пайплайны, стадии, задачи и append-only логи задач. Данные PostgreSQL сохраняются Docker volume `cicd_postgres_data`; доступ с хоста опубликован на порту `22543` по умолчанию.

PostgreSQL — источник правды для control plane. Dashboard и CLI не хранят копию состояния, а получают его через REST API. Артефакты, cache, удалённое исполнение и долговременное хранилище логов пока не реализованы и не должны имитироваться локальными файлами контейнера.

## Данные и границы ответственности

| Тип данных | Текущее расположение | Политика MVP |
|---|---|---|
| Метаданные проектов и пайплайнов | PostgreSQL | постоянное хранение |
| Статусы stage/job | PostgreSQL | транзакционные изменения с доменной валидацией |
| Логи job | PostgreSQL, append-only | записи упорядочены и доступны через API |
| Артефакты job | отсутствуют | запланировано S3-совместимое хранилище |
| Кэш сборок | отсутствует | запланирован отдельно от артефактов |

Локальная файловая система API-контейнера не является durable storage. Удаление или пересоздание контейнера не должно быть способом управления данными PostgreSQL; для этого используются миграции и резервные копии.

## План: S3-совместимое хранилище артефактов

После появления реальных runner-ов артефакты будут размещаться в S3-совместимом объектном хранилище: AWS S3, MinIO или совместимом self-hosted сервисе. PostgreSQL будет хранить только метаданные: владельца job, ключ объекта, размер, checksum, MIME type, время создания, срок хранения и статус удаления.

- Ключ объекта должен включать project/pipeline/job/attempt и не позволять traversal или коллизию имён пользователя.
- Загрузка идёт через ограниченные по времени presigned URL либо через API с потоковой передачей; секреты object storage не выдаются браузеру.
- Артефакт становится доступен только после проверки успешной загрузки и checksum.
- Политика retention определяет срок жизни по проекту и типу job; удаление должно быть идемпотентным и наблюдаемым.
- Доступ к скачиванию будет проверять будущая модель аутентификации и RBAC.

## Retention логов

В MVP логи не имеют автоматического срока удаления. До включения массового исполнения это упрощает аудит, но требует контроля роста базы. При переходе к runner-ам необходимо ввести настраиваемую retention policy:

- отдельные сроки для успешных, failed и canceled job;
- лимиты размера одной записи и общего объёма логов job;
- асинхронную пакетную очистку старых логов с audit-записью;
- возможность сохранить логи для закреплённого pipeline или расследования;
- метрики объёма и возраста логов, предупреждающие до исчерпания диска.

Очистка логов не должна ломать статусную историю: можно удалить payload лога, сохранив метаданные job и факт применения retention policy.

## Резервное копирование PostgreSQL

Стратегия резервного копирования обязательна до production-развёртывания. Базовая политика: ежедневный логический backup `pg_dump` в custom format, хранение в отдельном durable/S3-совместимом хранилище, шифрование и ограниченный доступ. Для более строгих RPO/RTO следует дополнить её физическими backup и WAL-архивацией.

Минимальные операционные требования:

1. Хранить backup вне Docker volume и вне единственного узла PostgreSQL.
2. Задать retention, например daily/weekly/monthly, исходя из согласованных RPO/RTO.
3. Передавать credentials через защищённые `CICD_` переменные или secret manager, не через Git.
4. Периодически выполнять восстановление в изолированную БД и проверять API-запросами целостность проектов, пайплайнов, job и логов.
5. Документировать дату последнего успешного backup, результат restore drill и ответственного оператора.

Пример логического backup для операционного окружения:

```bash
pg_dump --format=custom --no-owner --file forge-cicd.dump "$CICD_DATABASE_URL"
```

Команда иллюстративна: production-процедура должна также передавать файл в защищённое внешнее хранилище и проверять код завершения.
